# Reading

Run `migrations/011_reading_library.sql` in Supabase SQL Editor. Reading uses account-scoped IndexedDB tables `readingFolders` and `readingArticles` (database version 5) and separate Supabase tables with owner RLS and a composite folder-owner FK. Vocabulary sync/import/export never clears Reading tables. Reading records are saved locally first; folder then article writes are queued and sent to Supabase. On mount, online and manual refresh pending writes retry before downloading cloud data. Article deletion uses a tombstone; vocabulary cards remain unchanged. Folder create/rename is available; folders are currently one level, with articles as the child rows.

A Reading article contains a title, folder, HTML content and separate plain-text note. The editor accepts HTML source and offers a sanitized preview. Rendering is sanitized with [DOMPurify](https://github.com/cure53/DOMPurify), restricted to semantic HTML tags and a small attribute allowlist. Scripts, event handlers, embedded documents, arbitrary styles and forged vocabulary-link attributes are stripped. Generated links use DOM text/attribute APIs, not string interpolation.

Detection is explicit: creating, opening or saving an article does not search the vocabulary library. Clicking **Detect vocab** reads local vocabulary and stores a snapshot of the sanitized source with text offsets and note IDs. It runs locally, makes no AI request and adds no vocabulary. Matching is case-insensitive, whole-word/phrase, prioritizes the longest match and supports words split across inline markup. Phrases do not cross paragraphs; preformatted/code and existing links are skipped. Matching is literal (not AI stemming/lemmatization). Duplicate words choose the lexicographically first note ID. Maximum content is 200,000 characters and 20,000 matched occurrences; detection yields periodically and cancels when navigating away.

The HTML source is kept separate from detected links. Editing HTML clears detection. Deleting a vocabulary card removes its link from rendered content without scanning again. Newly added vocabulary requires another Detect vocab click. Links open the existing vocabulary-card popup via the note query parameter. Ordinary text remains selectable and uses the shared selection-to-add-vocabulary menu.

`server/reading-content.test.mjs` verifies HTML sanitization, matching, inline markup, overlap/word boundaries, invalidation, deleted cards and cancellation with jsdom. `server/reading-storage.test.mjs` verifies folder ownership, note/content preservation, tombstones and real local PostgreSQL RLS via PGlite. These tests do not deploy to a live Supabase project.

## Typed study notes

Run `migrations/012_reading_study_notes.sql` after 011. Notes are no longer part of the article editor. Each study note has its own ID, owner, article ID, type (`grammar`, `sentence_structure`, `expression`, `other`), title, content, optional source quote and timestamps. The account-scoped local `readingStudyNotes` table (DB version 6) and Supabase `reading_study_notes` table are independent from articles. The `(owner_id,note_type)` index supports a future Grammar section; the article ID retains the original lesson context. That future tab is not implemented yet.

Creating or editing a study note does not modify article content, detection or article timestamps. Notes sync after folders/articles and have their own pending status and tombstones. Deleting an article also tombstones its locally available study notes. A future global notes view must exclude notes whose parent article is deleted as well as note tombstones.

Legacy article note text is retained as a separate `other` note called “Ghi chú cũ”, both locally and in SQL migration 012. Its note ID equals its article ID in the separate table, preventing duplication when syncing the migration across devices. The deprecated article note field remains only for compatibility and is not editable in the article form.

## Vocabulary backlinks

After Detect vocab, saving the article updates editable matched vocabulary notes in the same local transaction. Each article has one reserved `values['__readingSource:<article-id>']` JSON entry per matched note, containing the owner, title, context excerpt, occurrence count and detection date. Other articles and card fields are preserved. Existing vocabulary row sync persists this metadata through `field_values` and existing JSON backups include it, so no new SQL migration is required. Read-only vocabulary is not modified.

Backlinks appear under “Nguồn bài đọc” in the AI card answer and in other card previews/answers. Links return to `/reading/articles/:id?sourceNote=:noteId`, highlight matching links and scroll the Content pane to the first occurrence. Only the source owner's Reading links are displayed. Editing source content or deleting the source article removes that article's backlink metadata locally; changing its title updates it. Older detections need one Detect vocab run to populate backlinks and context. Source metadata and Reading data sync through separate existing queues; offline changes remain local until those syncs succeed.
